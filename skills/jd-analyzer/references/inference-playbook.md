# 역추론 플레이북

추상적인 채용공고에서 실제 업무를 복원하는 방법별 상세 절차.

---

## 방법 A. 동일 직무 타사 공고 대조

### 절차

1. 공고의 직무명을 정규화한다
   - "Data Platform Engineer", "데이터 플랫폼 엔지니어", "데이터 엔지니어" 는 같은 군으로 묶는다
2. 웹 검색으로 동일 직무 공고를 5~10건 수집한다
   ```
   "{직무명}" 채용 주요업무 자격요건
   site:wanted.co.kr "{직무명}"
   site:jumpit.co.kr "{직무명}"
   ```
3. 업무 항목을 모아 빈도표를 만든다
4. 분류한다

| 분류 | 판정 기준 | 의미 |
|---|---|---|
| 공통 업무 | 7건 이상에서 등장 | 이 직무의 기본기. 못 하면 지원 자체가 어려움 |
| 준공통 | 3~6건 | 회사 성격에 따라 갈리는 업무 |
| **특이 업무** | 1~2건, 이 공고 포함 | **이 회사가 실제로 원하는 것. 지원서의 핵심 소재** |
| 누락 항목 | 타사엔 흔한데 이 공고엔 없음 | 이 회사에서는 다른 팀이 담당하거나, 아직 안 하는 영역 |

### 해석 예시

```
공고 문구: "데이터 기반 의사결정을 지원합니다"

타사 대조 결과:
  공통  : 데이터 파이프라인 구축/운영 (9/10)
  공통  : 데이터 품질 관리 (7/10)
  특이  : 사내 실험 플랫폼 운영 (2/10, 이 공고 포함)
  누락  : ML 모델 서빙 (6/10에 있으나 이 공고엔 없음)

복원된 실제 업무:
  파이프라인 운영이 기본이되, 이 회사는 A/B 테스트 인프라를 직접 다루는 자리.
  ML 서빙은 별도 팀이 있을 가능성.

지원서 전략:
  실험 설계와 통계적 유의성 검증 경험을 전면에 배치.
```

### 주의

- 타사 공고를 그대로 인용하지 않는다. 패턴 추출에만 사용한다
- 공고 게시 시점을 확인한다. 1년 이상 지난 공고는 직무 정의가 달라졌을 수 있다

## 방법 B. 기술 스택 역추론

### 개발 직군

| 스택 조합 | 추론되는 시스템·업무 | 함께 따라오는 것 |
|---|---|---|
| Kafka + Flink/Spark Streaming | 실시간 스트리밍 파이프라인 | 장애 대응, 온콜 가능성 |
| Airflow + dbt + DW | 배치 ETL 중심 | SQL 비중 높음, 데이터 모델링 |
| Spring Boot + MSA + Kubernetes | 서비스 분리 진행/완료 | 도메인 경계 설계, 분산 트랜잭션 |
| 레거시 + 신규 스택 병기 | 마이그레이션 프로젝트 | 이관 경험이 실질 필수 요건 |
| Terraform + ArgoCD + K8s | 플랫폼 엔지니어링 | 개발자 경험 개선, 내부 도구 |
| React + Next.js + SSR 언급 | SEO 또는 초기 렌더링 성능이 사업적으로 중요 | 성능 예산, 코어웹바이탈 |
| 모바일 + 크로스플랫폼 병기 | 앱 통합 또는 전환 검토 중 | 네이티브 브릿지 |
| PyTorch + 서빙 프레임워크 | 연구가 아니라 프로덕션 ML | 지연시간·비용 최적화 |

### 비개발 직군

| 도구 조합 | 추론되는 업무 성격 |
|---|---|
| Salesforce + Tableau | 세일즈 오퍼레이션. 데이터 기반 영업 관리 |
| GA4 + Amplitude + SQL | 프로덕트 애널리틱스. 그로스 조직 소속 가능성 |
| Figma + 디자인시스템 언급 | 컴포넌트 단위 협업. 개발자와 밀접 |
| Jira + Confluence + 애자일 | 프로세스가 정립된 조직 |
| 특정 ERP 명시 | 그 시스템 운영·개선이 업무의 상당 부분 |

### 해석 규칙

- 스택 나열이 지나치게 많으면(10개 이상) 1인 다역이거나 인사팀 템플릿일 가능성
- 버전이 명시되면(Java 8, Python 3.8 등) 실제 운영 환경일 확률이 높다
- "경험 있으면 좋음" 으로만 나열된 스택은 실제로는 안 쓸 수도 있다

## 방법 C. 회사 공개 자료 대조

### 기술블로그

**최근 글의 주제가 곧 그 팀의 현재 과제다.**

절차:
1. 회사 기술블로그를 웹 조회로 수집
2. 최근 12개월 글 목록을 뽑고 주제를 분류
3. 공고의 팀과 매칭되는 글을 찾는다
4. 글에서 언급된 문제 상황이 곧 입사 후 마주할 과제

```
공고: "백엔드 개발자 (결제 플랫폼)"
블로그: "결제 정산 배치의 정합성을 보장하는 방법" (2026-03)
        "PG사 이중화 전환기" (2026-01)

추론: 정산 정합성과 PG 이중화가 최근 과제.
      면접에서 분산 트랜잭션, 멱등성, 정산 대사 관련 질문 가능성 높음.
확신도: 높음 (팀 매칭이 명확)
```

블로그가 1년 이상 방치되어 있으면 그 자체가 신호다.
company-diligence 의 운영 계열 경고 신호로 넘긴다.

### 같은 팀의 다른 공고

채용 페이지에서 동일 조직명으로 열려 있는 다른 공고를 본다.

```
같은 팀에서 동시 채용 중:
  - 백엔드 개발자
  - 데이터 엔지니어
  - 프로덕트 매니저

추론: 신규 프로덕트 조직을 세우는 중.
      초기 세팅 업무가 많고 기존 체계가 없을 가능성.
```

### 기타 공개 신호

- 컨퍼런스 발표 자료: 회사가 자랑하고 싶은 기술 = 실제 투자 영역
- 오픈소스 저장소: 실제 코드 스타일과 기술 성숙도 확인 가능
- 링크드인 팀원 프로필: 팀 구성, 평균 연차, 전 직장 분포
- 앱스토어 리뷰: 프로덕트가 현재 겪는 문제 (프로덕트 직군에 유용)

## 방법 D. 조직 맥락 추론

### 신설 vs 충원 판별

| 신호 | 판정 |
|---|---|
| "새롭게 시작하는", "0에서 1을" | 신설 |
| 같은 팀 여러 직군 동시 채용 | 신설 조직 |
| 공고에 기존 시스템 설명이 상세 | 충원 |
| 동일 공고 재게시 이력 | 충원, 또는 채용 난항 |
| "기존 팀에 합류하여" | 충원 |

**신설**이면: 초기 세팅 경험, 자율성, 체계 부재 감수 능력이 실제 요건
**충원**이면: 기존 시스템 파악 속도, 인수인계 능력이 실제 요건
공고에는 둘 다 안 써 있지만 면접에서는 이것이 갈린다.

### 성장 국면 vs 유지보수 국면

| 신호 | 국면 |
|---|---|
| 신규 서비스 언급, 확장, 신규 시장 | 성장 |
| 안정화, 개선, 고도화, 운영 효율 | 유지보수 |
| 마이그레이션, 전환, 현대화 | 부채 상환 |
| 비용 최적화, 효율화 반복 | 긴축 국면일 수 있음 |

마지막 항목은 company-diligence 로 넘겨 재무 신호와 교차검증할 가치가 있다.

## 확신도 표기 기준

모든 추론에는 확신도를 붙인다.

| 확신도 | 기준 |
|---|---|
| 높음 | 독립적인 근거 2개 이상이 같은 방향을 가리킴 |
| 중간 | 근거 1개, 또는 근거들이 간접적 |
| 낮음 | 정황상 추정. 반대 해석도 가능 |

확신도 "낮음" 항목은 면접에서 단정적으로 말하지 말라고 지원자에게 안내한다.
틀린 전제로 말하면 준비 부족보다 더 나쁜 인상을 준다.
