# 경험 마스터 데이터 스키마

이력서 커스터마이징의 품질은 마스터 데이터의 품질에 비례한다.

## 필드별 작성 지침

### 역할
"백엔드 개발"처럼 쓰지 않는다. **팀 내 위치와 담당 범위**를 쓴다.
```
나쁨: 백엔드 개발
좋음: 백엔드 3인 중 리드, 결제·정산 도메인 전담, PG사 커뮤니케이션 담당
```

### 문제 상황
기술적 문제만 쓰지 않는다. **왜 그게 문제였는지**를 사업 맥락으로 쓴다.
```
나쁨: API 응답이 느렸다
좋음: 결제 API 응답이 3초를 넘어 이탈률이 상승했고, 피크 시간대 결제 실패가 매출에 직접 영향
```

### 행동 - 의사결정 기록이 핵심
"무엇을 썼다"보다 **"왜 그것을 골랐는가"**가 면접에서 변별력을 만든다.
검토했지만 선택하지 않은 대안을 기록해두면 면접 답변의 깊이가 달라진다.

### 결과 - 측정 방법까지
```
나쁨: 성능을 개선했다
보통: 응답시간을 3초에서 0.4초로 단축
좋음: 결제 API p95 응답시간을 3.2초에서 0.4초로 단축
      (APM 기준, 개선 전후 각 2주 평균, 확정치)
```

### 기여도 - 정직하게
| 표기 | 의미 |
|---|---|
| 주도 | 내가 설계하고 의사결정했고 실행을 이끌었다 |
| 공동 주도 | 동등한 위치에서 함께 결정했다 |
| 참여 | 정해진 방향에서 내 몫을 구현했다 |
| 지원 | 부분적으로 도왔다 |

이력서에서는 "주도"를 강조하고 싶지만, 마스터 데이터에는 정확히 기록한다.
면접에서 파고들면 금방 드러나기 때문이다.

### 약점 - 반드시 기록
각 경험의 한계를 미리 적어둔다.
```
약점: 트래픽 규모가 크지 않아 대규모 분산 환경 경험으로 보기는 어려움.
      대규모 서비스 공고에서는 이 점을 인정하고 학습 계획으로 보완할 것.
```
면접에서 먼저 인정하고 대응 계획을 말하는 것이 방어하다 무너지는 것보다 낫다.

## 사이드 프로젝트 처리

`side-projects.md`에 별도 관리한다.

포함 기준:
- 실제 사용자가 있었는가 (없으면 학습용으로 표기)
- 배포되어 운영되었는가
- 기술적 의사결정이 있었는가

**튜토리얼을 따라 만든 것은 넣지 않는다.** 오히려 마이너스가 된다.
경력이 없을 때만 학습 증거로 제한적으로 사용한다.

## 데이터 축적 습관

- 프로젝트가 끝난 직후에 기록한다. 6개월 지나면 수치를 기억하지 못한다
- 지표는 스크린샷이나 링크로 근거를 남긴다 (회사 자산이므로 반출 주의, 수치만 메모)
- 회고 문서, 발표 자료, PR 설명이 좋은 원천 자료다
- 분기에 한 번 마스터 데이터를 갱신한다

**보안 주의**: 회사의 비공개 지표, 고객사명, 내부 시스템 상세는 마스터 데이터에는 기록하되
외부 제출 이력서에서는 일반화한다.
```
마스터: A은행 대상 계좌 연동 시스템, 일 300만 건
이력서: 금융권 고객사 대상 계좌 연동 시스템, 일 300만 건 규모
```
